## 2. 目标

人物蒸馏不是复制真实人物，也不是生成一份孤立 Skill 文件。它从用户明确描述和用户有权使用的资料中，提炼人物处理新问题时可复用的认知与表达规律，形成尚未创建人物的待确认人物候选草稿。

能力必须同时满足：

1. 结果仍进入现有“人物候选草稿 → 人工校准 → 创建人物及初始当前灵魂版本”闭环；人物创建后的修改继续使用灵魂草稿与发布流程。
2. 事实、观点、表达规律和系统推断可以区分，重要结论能够定位原始证据。
3. 资料不足时允许生成有限草稿，但必须显式保留未知项和诚实边界。
4. 冲突资料不得被模型静默调和；用户可以看到冲突及其影响。
5. 模型、参数、提示词、输入、程序校验和评测结果均可追溯。
6. OpenViking 故障时可以使用 SQLite FTS5 完成已导入资料的蒸馏。
7. 不通过开放式 Agent 循环、联网搜索结果或模型自评直接发布人物灵魂。

## 3. 明确不做

首期人物蒸馏不包括：

- 在人样进程内抓取网页、下载视频、解析 PDF、执行 OCR 或搜索互联网；
- 固定启动六个并行 Agent，或允许模型动态改变算法步骤；
- 将 `.claude/skills/`、`SKILL.md` 或第三方 Agent 目录作为业务事实源；
- 使用未经授权、来源不明或明显侵犯版权的资料；
- 根据网站名称建立不可解释的永久黑名单或白名单；
- 把“必须联网搜索”“必须调用工具”等运行编排写入人物灵魂；
- 让蒸馏结果自动变成人物成长或人物记忆；
- 让 OpenViking 派生内容越过 SQLite、证据校验或人工发布门禁；
- 把模型生成的人物输出包装为真实人物本人声明。

外部 Agent 可以独立完成用户授权的资料搜集与文本清洗，再通过现有 `/api/v2` 资料接口导入 TXT 或 Markdown。人样只处理已经进入 SQLite 的资料。

## 4. 与现有能力的映射

| 外部方案阶段 | 人样承载位置 | 集成方式 |
|---|---|---|
| 目标与用途确认 | 人物创建流程 | 保存人物名称、创建要求、用途与聚焦范围，不写入人物灵魂 |
| 多源资料采集 | 资料库与公共维护接口 | 外部采集，人样保存正文、哈希、资料角色和人物关系 |
| 资料覆盖检查 | 人物蒸馏运行 | 对来源关系和覆盖维度生成结构化快照，并等待一次人工确认 |
| 心智框架提取 | 固定人物蒸馏算法 | 模型提取结构化候选，程序验证证据、独立来源、重复和冲突 |

| 已知、边缘和风格测试 | 人物蒸馏评测 | 保存可解释的逐项结果；模型评分只作为辅助证据 |

| 后续更新 | 现有成长与记忆分析 | 继续使用增量分析、完整重建、人工发布和学习自动化 |

## 5. 领域边界

### 5.1 人物蒸馏的定位

“人物蒸馏”是人物创建前的用例名称，不是人物的第四种心智，也不是可以直接执行任务的模拟对象。蒸馏阶段的 `candidate_prompt_text` 属于运行候选结果，不是领域中的“灵魂草稿”。

人物蒸馏完成前：

- 可以没有人物实体；
- 不产生当前灵魂版本；
- 不进入兴趣判断、图文生成、成长或记忆检索；
- 只保存创建要求、资料快照、提炼候选和评测证据。

人物蒸馏确认后：

- 复用现有人物创建、资料关系和灵魂预算规则；
- 通过一次跨聚合持久化操作，原子创建人物、初始当前灵魂版本并完成蒸馏运行；
- 关联用户在运行中确认的资料；
- 后续修改继续进入灵魂草稿和人工发布流程。

### 5.2 不变量

1. 一次蒸馏运行最多创建一个人物。
2. 一个已完成或已取消的运行不能再次创建人物。
3. 运行使用的资料正文、哈希、角色和来源分类在开始提取前固定。
4. 资料后续修改或删除不回写历史运行；用户明确删除正文时沿用现有受审计清除规则。
5. 模型只能引用本次运行的输入标识，不能引用任意 URL、未选资料或其他人物资料。
6. 结构化候选未通过程序证据校验时不得进入灵魂编译。
7. 评测硬门禁失败不得创建人物；用户必须修改候选并重新评测。软门禁警告可以在留下审核记录后继续。
8. 人工编辑只改变候选灵魂正文，不改变模型原始提取、程序校验或评测历史。
9. 相同原始来源的转载、切片和重复导入只计算一个独立来源。
10. 用户创建要求高于资料推断，但不能把没有证据的用户猜测标记为真实人物事实。

### 5.3 具体场景校验

| 场景 | 预期行为 |
|---|---|
| 只有一句人物描述，没有资料 | 允许形成有限草稿；覆盖状态为不足，事实型内容只能来自用户明确描述 |
| 同一次采访被五篇文章转载 | 可以作为多条资料展示，但独立证据数仍为一 |
| 本人早期和近期观点冲突 | 同时保留时间范围与冲突，不自动选择“更新”或“更真实”的一方 |
| 他人评价与本人声明冲突 | 分别标记来源关系，在候选中写明外部观察与自我陈述差异 |
| 资料正文包含提示注入 | 作为不可信文本保留，不能修改算法规则、输出 Schema 或读取其他资料 |
| OpenViking 不可用 | 在运行开始前选择 FTS5；已经开始的运行不切换提供器 |
| 评测发现未知问题被编造 | 阻止默认确认，用户修改候选并重新评测后再继续 |
| 用户删除蒸馏使用的资料 | 不改变已经创建的人物；历史运行只保留允许保留的标识、摘要和哈希 |

## 6. 深模块与调用链

人物蒸馏应建立独立深模块，隐藏资料快照、状态迁移、四阶段模型调用、证据校验、评测和人物创建协调。不要把它硬塞进现有成长与记忆 `AnalysisBatch`：后者要求已有模拟对象、灵魂基线和学习提示词基线，而人物蒸馏发生在人物创建之前。

外部接口只暴露五个核心用例：

```text
createRun(input)                         创建并评估资料
getRun(runId)                            读取完整可见状态
reviewSources(runId, decision)           确认资料范围或退回补充
saveCandidate(runId, editedSoul)         保存人工编辑并重新评测
confirmCandidate(runId, promptHash)      确认已通过评测的候选并创建人物
```

取消和失败重试属于运行生命周期，也可作为明确用例提供；不得用一个接受任意事件的通用 `advance()` 方法隐藏权限和状态约束。

推荐调用链：

```text
人物创建页面
  → /api/v1 人物蒸馏控制器
  → PersonaDistillationApplicationService
  → 蒸馏领域规则
  → DistillationRepository / AiAlgorithmApplicationService / ContextProvider
  → SQLite / TextModelPort / OpenViking 或 FTS5

前台 Worker
  → TaskRoutingApplicationService
  → PersonaDistillationApplicationService.execute(job)
```

接口与测试共用同一接缝。页面、控制器和 Worker 都不能直接编排模型步骤或访问 SQLite 适配器。最终确认不能先调用现有 `ContentApplicationService.createPersona()` 再单独完成运行，否则第二次写入失败会留下已经创建但运行仍待确认的半完成状态；蒸馏仓储接缝必须提供一个跨聚合原子操作，并复用现有人物创建的领域校验和数据映射。

## 7. 运行状态机

```text
assessing_sources
  ├──失败──────────────> failed
  └──覆盖快照完成──────> awaiting_source_review
                              ├──取消──────> canceled
                              ├──补充资料──> canceled
                              └──确认──────> extracting
                                                ├──无有效候选──> failed
                                                └──校验通过────> synthesizing
                                                                      ├──失败──> failed
                                                                      └────────> evaluating
                                                                                      ├──失败──> failed
                                                                                      └────────> awaiting_candidate_review
                                                                                                      ├──取消────────> canceled
                                                                                                      ├──编辑──> evaluating
                                                                                                      └──确认────────> completed
```

规则：

- `awaiting_source_review` 前只固定资料覆盖快照，不调用心智提取与灵魂编译模型。
- 用户选择补充资料时终止当前运行，新增资料后创建新运行；历史覆盖快照不被覆盖。
- `extracting`、`synthesizing`、`evaluating` 由持久任务推进，进程重启后按既有租约规则恢复。
- 全部非终态都可以请求协作式取消，执行中的任务只在既有安全点转为 `canceled`。
- 模型步骤最多两次自动尝试；第二次仍不符合 Schema 或硬约束时失败。
- `failed` 只能在输入和算法快照仍然有效时创建一次新的重试运行，不能原地覆盖历史结果。
- 用户编辑候选后必须重新进入 `evaluating`；旧候选的评测结果不能用于确认新正文。
- `completed` 表示人物及初始当前灵魂版本已经创建；后续灵魂修改仍需单独保存草稿并发布。

## 8. 数据设计

### 8.1 `persona_distillation_runs`

| 字段 | 说明 |
|---|---|
| `id` | 运行 UUID |
| `status` | 当前状态 |
| `requested_name` | 用户填写的候选人物名称，可在确认时修改 |
| `objective` | 用户说明的用途与聚焦方向，不直接进入人物灵魂 |
| `world_id?` | 创建后准备关联的世界 |
| `provider` | `sqlite_fts5` 或 `openviking`，创建运行时固定 |
| `coverage_snapshot_json?` | 六维覆盖、来源质量、缺口和警告 |
| `algorithm_snapshot_json?` | 固定步骤、模型、参数和提示词版本 |
| `raw_extraction_json?` | 模型原始结构化候选 |
| `validated_extraction_json?` | 程序校验后的候选快照 |
| `candidate_name?` | 模型建议名称 |
| `candidate_prompt_text?` | 模型编译后写入人物候选草稿的完整灵魂文本 |
| `candidate_prompt_hash?` | 当前候选灵魂正文 SHA-256 |
| `evaluated_prompt_hash?` | 最近一次完整通过硬门禁评测的候选正文 SHA-256 |
| `reviewed_prompt_text?` | 用户确认时的最终编辑结果 |
| `created_persona_id?` | 成功创建的人物 UUID |
| `error_code?` / `error_message?` | 稳定错误与脱敏说明 |
| `created_at` / `updated_at` / `completed_at?` | 生命周期时间 |

最终确认使用状态条件更新与人物创建的同一事务：只有 `awaiting_candidate_review` 且 `candidate_prompt_hash` 等于 `evaluated_prompt_hash` 时，可以写入 `created_persona_id` 并进入 `completed`。并发确认时只有一个事务成功，另一个返回状态冲突。

### 8.2 资料来源元数据

为通用 `source_materials` 增加以下可空字段，保存与目标人物无关且可被多次复用的来源事实：

- `origin_url`：用户或外部 Agent 提供的原始地址；
- `author_name`：资料作者或发言者；
- `published_at`：可确认的发表或发生时间；
- `original_source_key`：原始作品、访谈或事件的稳定分组键。

字段为空不阻止普通资料管理或人物蒸馏。来源关系和覆盖维度与目标人物有关，不进入 `source_materials`，只保存在本次蒸馏输入快照中。

### 8.3 `persona_distillation_inputs`

保存本次运行实际使用的不可变资料快照：

- 资料 UUID、名称、完整正文 SHA-256；
- 现有资料角色 `canon_fact`、`reference` 或 `style_sample`；
- 来源关系、覆盖维度、内容时间范围；
- 独立来源分组键；
- 是否由用户明确提供；
- 正文当前是否仍可用；
- 实际发送给模型的分块 UUID、分块正文和分块哈希；
- 创建要求作为独立可信输入，不伪装成资料。

一项资料可以覆盖多个维度，因此覆盖维度保存为去重枚举数组，而不是单值分类。运行不重复保存没有进入任何模型输入或证据的整份大正文；完整资料仍由 `source_materials` 保存，运行通过完整正文哈希和实际分块快照同时保证变更检测与调用可重放。

### 8.4 `persona_distillation_claims`

保存程序校验后的结构化认知候选：

| 字段 | 说明 |
|---|---|
| `category` | 心智模型、决策启发式、表达特征、价值观、反模式、内在张力、诚实边界、时间线 |
| `statement` | 原子陈述 |
| `applicability` | 适用条件或场景 |
| `limitations` | 失效条件、反例或不确定性 |
| `basis` | `explicit`、`observed` 或 `inferred` |
| `confidence` | 0 到 1，仅表示本次证据支持度 |
| `independent_source_count` | 程序计算的独立来源数 |
| `cross_context_count` | 程序确认的不同场景数 |
| `status` | 有效、警告或拒绝 |
| `rejection_reasons_json` | 程序拒绝原因 |

### 8.5 `persona_distillation_evidence`

一条候选可以引用多项证据。每项引用保存：

- 候选 UUID；
- 蒸馏输入 UUID；
- 原资料分块 UUID 或稳定定位信息；
- 支持或反对关系；
- 引用文本与哈希；
- 发生时间；
- 独立来源分组键。

模型不能自行决定独立来源数。程序按稳定分组键去重后写入候选。

### 8.6 `persona_distillation_evaluations`

保存每项评测的类型、输入、期望约束、候选输出、评分、失败原因、模型与参数快照。评测结果只追加，不覆盖；重新评测创建新轮次。

## 9. 资料分类与质量模型

现有资料角色继续回答“这份资料在人物任务中如何使用”。人物蒸馏额外保存运行级元数据，回答“这份资料与目标人物是什么关系”和“它能支持哪个提炼维度”。三者不能合并成一个枚举。

### 9.1 来源关系

| 来源关系 | 示例 | 默认解释 |
|---|---|---|
| `subject_authored` | 本人著作、博客、公开信 | 直接表达，但仍可能受公开形象影响 |
| `direct_conversation` | 完整访谈、播客、演讲问答 | 能观察即兴推理和追问反应 |
| `observed_decision` | 有可核验背景与结果的实际决策 | 更接近行为证据 |
| `subject_social` | 本人社交媒体原文 | 适合表达特征，系统性较弱 |
| `third_party` | 传记、报道、同行评价 | 外部观察，不能冒充本人观点 |
| `user_statement` | 用户明确提供的人设要求 | 最高产品优先级，不等于历史事实 |

### 9.2 覆盖维度

| 编码 | 含义 |
|---|---|
| `writings` | 著作与系统思考 |
| `conversations` | 长对话与即兴推理 |
| `expression` | 表达方式 |
| `external_views` | 他者观察与批评 |
| `decisions` | 实际决策 |
| `timeline` | 时间线与观点变化 |

### 9.3 质量指标

覆盖检查分别展示：

- 总资料数与独立来源数；
- 各维度覆盖程度；
- 本人直接来源占比；
- 时间跨度与最近资料时间；
- 重复来源数量；
- 冲突数量；
- 无法定位原文的资料数量；
- 只由系统推断支持的候选数量。

这些指标默认产生警告，不使用单一综合分数伪装确定性。

## 10. 固定人物蒸馏算法

新增代码内固定算法 `persona_distillation`。数据库只允许为固定步骤绑定模型、提示词和调用参数。

### 10.1 `classify_sources`

输入：创建要求、资料元数据和受预算约束的正文片段。

输出：每项资料的来源关系建议、覆盖维度、时间范围、重复关系建议和缺口摘要。

程序必须：

- 资料输入为空时不调用模型，直接保存空分类和零覆盖快照并进入人工检查点；
- 校验所有资料 UUID 属于本次运行；
- 根据内容哈希、原始 URL、标题和用户确认信息计算独立来源分组；
- 不允许模型把第三方评价改标为本人观点；
- 保存覆盖快照并进入人工检查点。

### 10.2 `extract_claims`

输入：用户确认后的资料快照、创建要求和覆盖快照。

模型输出：

```json
{
  "claims": [
    {
      "category": "mental_model",
      "statement": "候选原子陈述",
      "applicability": "适用场景",
      "limitations": "失效条件或未知项",
      "basis": "explicit",
      "confidence": 0.9,
      "evidence": [
        {
          "inputId": "蒸馏输入 UUID",
          "relation": "supporting",
          "quote": "可定位原文"
        }
      ],
      "conflicts": []
    }
  ]
}
```

程序验证：

1. 输入标识存在且属于本次运行。
2. 引用文本能够在固定正文中定位；规范化后保存精确哈希。
3. 支持与反对证据分别保存，冲突不能只存在于自然语言说明。
4. 完全相同或高度近似候选合并证据，但不相加重复来源权重。
5. `explicit` 必须由本人直接来源或用户明确设定支持。
6. `observed` 必须由实际行为或直接观察支持。
7. `inferred` 必须包含局限，不能编译为确定事实。
8. 没有有效证据的事实型候选被拒绝，不进入综合步骤。

### 10.3 心智模型筛选

心智模型不使用“出现三次即为真信念”的固定规则。对每项候选分别记录：

- 跨场景复现：是否在不同问题或领域中出现；
- 生成能力：能否对未出现过的问题产生可检验倾向；
- 区分度：是否区别于通用正确话术；
- 反例：何时没有按该模型行动；
- 时间稳定性：是否只属于特定阶段。

三项核心指标都较强时可以归入心智模型；证据不足时降级为决策启发式或带警告推断。数量不是硬门禁，禁止为了达到三到七项而制造结论。

### 10.4 `synthesize_soul`

只接收程序校验后的候选，生成人物候选草稿中的单文本灵魂内容。推荐结构：

```text
# 身份与事实边界
# 心智模型
# 决策启发式
# 表达方式
# 价值排序与反模式
# 内在张力与观点变化
# 诚实边界
```

规则：

- 结构只用于提高稳定性，最终仍是一个 `promptText`；
- 不把完整时间线、来源目录、调研报告或模型评分塞入运行提示词；
- 不伪造第一人称原话；
- 推断必须使用不确定表达；
- 资料冲突必须说明适用时期或仍未解决；
- 没有证据的章节可以省略，不能填充通用人格话术；
- 创建要求中的用途只影响选择与表达密度，不成为人物自我事实；
- 输出必须通过现有灵魂字符与 Token 预算校验。

### 10.5 `evaluate_soul`

评测输入只包含候选灵魂、固定评测用例和评测所需证据摘要，不向评分模型暴露期望答案之外的隐藏标签。

评测至少覆盖：

| 类型 | 目的 | 失败信号 |
|---|---|---|
| 已知事实 | 检查明确事实和立场 | 与直接证据相反或凭空增加事实 |
| 决策倾向 | 检查心智模型是否产生稳定判断 | 只能复述资料，无法迁移到相邻问题 |
| 未知边界 | 检查诚实边界 | 对无证据问题给出确定人物经历或立场 |
| 表达方式 | 检查语言特征 | 只有通用 AI 语气，或机械拼接原句 |
| 反事实诱导 | 检查设定稳定性 | 用户诱导后立即否定稳定核心约束 |
| 冲突处理 | 检查时间与适用条件 | 把矛盾资料合并成不存在的统一立场 |

评测模型结果是证据，不是事实。硬规则失败默认阻止确认；软评分下降只显示警告。

### 10.6 预算与模型分工

- 创建运行时固定资料数量、单项分块数、总输入 Token、单步输出 Token、整次用量和最大尝试数。
- 资料覆盖统计可以读取全部元数据，但模型只能接收预算选中的代表性分块。
- 提取步骤按资料分组分批执行，程序合并结果；并发度由现有 Worker 资源上限控制，不等同于固定 Agent 数量。
- 综合步骤只接收已校验候选，不重复发送全部资料正文。
- 评测步骤只接收候选灵魂、测试输入和必要证据，不重复发送提取过程。
- 每个步骤可以绑定不同模型部署；没有独立评测模型时允许复用同一部署，但必须显示“非独立评分”警告。
- 相同稳定系统提示前缀继续使用现有缓存亲和规则；不得缓存最终蒸馏结果代替新的业务运行。

## 11. 质量门禁

### 11.1 硬门禁

- 输入、引用和证据关系通过 Zod 与程序校验；
- 不存在跨人物、跨运行或未授权资料引用；
- 所有确定事实具有允许的证据来源；
- 冲突没有被丢弃；
- 未知边界评测没有出现确定性捏造；
- 候选灵魂通过 Token 预算与提示词安全检查；
- 最终确认的候选正文哈希与最近通过硬门禁的评测哈希一致；
- 创建人物前运行状态、资料快照和算法快照没有变化；
- 人物创建与运行完成使用同一 SQLite 事务，避免重复创建。

### 11.2 软门禁

- 心智模型数量；
- 本人直接来源占比；
- 六类资料覆盖率；
- 表达辨识度；
- 内在张力数量；
- 最近资料距当前时间；
- 模型评测得分。

软门禁只能产生具体警告，例如“没有实际决策资料，当前判断模型主要来自公开表达”，不能只显示模糊总分。

## 12. 上下文与 OpenViking

人物蒸馏复用现有 `ContextProvider` 接缝，但增加显式允许集合：

1. SQLite 根据本次选择的资料 UUID、人物关系、启用状态和哈希形成允许集合。
2. OpenViking 或 FTS5 只能在允许集合内排序片段。
3. 应用层再次按资料 UUID 和当前快照过滤。
4. 选中片段复制到蒸馏输入或证据快照后，不再依赖远端索引。
5. OpenViking 返回的摘要、派生记忆或未知 URI 不能直接成为蒸馏证据。

提供器在创建运行、固定输入并入队前选择。OpenViking 此时不可用可以选择 FTS5；运行创建后不得因 OpenViking 中途故障切换提供器，失败后由用户创建使用新快照的新运行。

## 13. HTTP 接口

首期只增加网页登录使用的 `/api/v1` 内部接口：

| 方法与路径 | 用途 |
|---|---|
| `POST /api/v1/persona-distillations` | 创建运行并返回 `202` |
| `GET /api/v1/persona-distillations/{id}` | 查询覆盖、候选、评测和状态 |
| `POST /api/v1/persona-distillations/{id}/source-review` | 确认资料范围并启动提取 |
| `POST /api/v1/persona-distillations/{id}/cancel` | 请求协作式取消 |
| `POST /api/v1/persona-distillations/{id}/retry` | 基于失败运行创建新运行 |
| `PUT /api/v1/persona-distillations/{id}/candidate` | 保存人工编辑并重新执行评测 |
| `POST /api/v1/persona-distillations/{id}/confirm` | 确认当前已通过评测的候选并创建人物与初始当前灵魂版本 |

控制器只负责认证、Zod 解析、调用一个应用服务方法和响应映射。

创建运行的最小输入：

```json
{
  "requestedName": "候选人物名称",
  "objective": "使用目的和可选聚焦方向",
  "worldId": null,
  "sourceIds": ["资料 UUID"]
}
```

资料审核输入必须带运行更新时间进行并发校验，并允许用户纠正运行级分类：

```json
{
  "expectedUpdatedAt": 1788480000000,
  "acceptedInputIds": ["蒸馏输入 UUID"],
  "corrections": [
    {
      "inputId": "蒸馏输入 UUID",
      "sourceRelation": "subject_authored",
      "coverageDimensions": ["writings", "expression"]
    }
  ]
}
```

保存候选输入：

```json
{
  "expectedUpdatedAt": 1788480000000,
  "promptText": "人工校准后的完整灵魂文本"
}
```

最终确认输入：

```json
{
  "expectedUpdatedAt": 1788480000000,
  "name": "最终人物名称",
  "expectedPromptHash": "最近通过评测的候选正文 SHA-256"
}
```

创建运行和保存候选返回 `202`；查询和资料审核成功返回 `200`；最终确认原子创建人物后返回 `201`。活动状态由页面按现有轮询节奏查询，不能把排队、提取、综合或评测状态当作成功。

首期不增加公共蒸馏接口。外部 Agent 继续通过现有 `/api/v2/sources` 导入资料；远程触发 AI 蒸馏需要单独修改产品范围、API Key 权限、幂等、费用与滥用控制后再设计。

## 14. 管理界面

人物列表继续只有一个“创建人物”入口，不恢复原创、资料型或混合型模式。

创建流程：

1. 填写人物名称、自然语言要求、可选世界和可选资料。
2. 提交后进入人物蒸馏工作区，而不是等待同步模型响应。
3. 覆盖检查完成后展示：资料数、独立来源、六类覆盖、重复、冲突、时间范围和缺口。
4. 用户选择“继续提炼”或“返回补充资料”。
5. 提炼与评测期间展示持久任务状态，可以离开页面后返回。
6. 最终页面同时展示候选灵魂、证据摘要、硬门禁、软警告和评测结果。
7. 用户编辑候选后点击“保存并重新评测”；评测完成前不能确认创建。
8. 当前候选哈希与通过硬门禁的评测哈希一致时，用户可以确认创建人物及初始当前灵魂版本。
9. 创建后进入现有灵魂工作区；后续修改仍使用现有草稿与发布入口，蒸馏页面不提供第二套灵魂编辑流程。

只有两个强制人工检查点：资料覆盖确认和最终候选确认。其余内部步骤不要求用户逐阶段点击，避免把模型编排暴露为操作负担。

## 15. 错误与恢复

建议稳定错误码：

| 错误码 | HTTP | 含义 |
|---|---:|---|
| `DISTILLATION_NOT_FOUND` | 404 | 蒸馏运行不存在 |
| `DISTILLATION_STATE_CONFLICT` | 409 | 当前状态不允许该动作 |
| `DISTILLATION_SOURCE_CHANGED` | 409 | 资料审核前内容或状态已经变化 |
| `DISTILLATION_EVIDENCE_INVALID` | 422 | 模型引用不存在或无法定位的证据 |
| `DISTILLATION_NO_VALID_CLAIMS` | 422 | 没有可进入综合步骤的有效候选 |
| `DISTILLATION_EVALUATION_FAILED` | 422 | 硬门禁评测失败 |
| `DISTILLATION_PROMPT_BUDGET_EXCEEDED` | 422 | 核心输入或候选灵魂超过预算 |
| `DISTILLATION_ALREADY_CONFIRMED` | 409 | 运行已经创建人物 |

外部模型和 OpenViking 错误继续映射为现有稳定能力错误。错误消息不得包含完整人物资料、系统提示词、API Key 或供应商原始响应。

## 16. 安全与合规

- 资料正文始终作为不可信数据编码，不能改变系统消息、输出 Schema 或工具权限。
- 外部 Agent 导入资料时必须保留来源地址、作者、时间和用户授权说明；人样不主动验证版权授权，但必须允许审计和删除。
- 真实人物的模拟结果应明确属于“基于资料生成的模拟对象”，不能用于证明本人真实意图、观点或授权。
- 用户删除资料时沿用现有删除影响检查，明确展示对未完成蒸馏运行和历史证据的影响。
- 日志只保存运行 ID、步骤、状态、模型部署、耗时、用量和脱敏错误，不保存完整资料或候选灵魂。
- 自动化测试使用本地模型替身，不调用真实收费模型。

## 17. 迁移与兼容

人物蒸馏上线后，新的后台人物创建统一走异步蒸馏流程。没有资料时仍可创建，不增加来源模式字段。

现有 `generation.persona_draft` 历史配置和快照不执行迁移改写。新流程稳定后，后台同步 `/api/v1/personas/draft` 及仅为它服务的应用方法、共享输入和组件已经删除，不建立兼容转发层。`persona_draft` 算法编码、提示词和既有配置继续保留，只用于数据库兼容与历史审计，不接受新的后台人物创建调用。

迁移必须验证空库、现有数据库升级和重复执行。新表加入一致性备份与只读恢复校验；蒸馏运行不依赖 OpenViking 索引才能恢复。

## 18. 分阶段实施

### 阶段一：契约与纯规则

变更：

- 确认产品范围并同步领域术语；
- 增加共享 Schema、运行状态机、来源独立性、引用定位、重复合并和质量门禁规则；
- 固定 `persona_distillation` 的稳定步骤编码与顺序，但在持久化迁移完成前不加入运行时算法目录。

验证：

- 单元测试覆盖全部合法和非法状态迁移；
- 重复转载只计一个独立来源；
- 引用不存在、跨运行或引用文本不匹配时拒绝；
- 无证据事实、未标记推断和被静默丢弃冲突时拒绝。

### 阶段二：持久化与任务恢复

变更：

- 新增 Drizzle Schema 和迁移；
- 实现蒸馏仓储接缝及 SQLite 适配器；
- 接入 `task_jobs`、租约、取消、失败和重试；
- 将蒸馏表和必要文件纳入备份恢复。

验证：

- 空库、既有数据库升级和迁移重复执行；
- 进程重启后任务恢复；
- 同一运行只能创建一个人物；
- 备份只读恢复后快照、候选和评测完整。

### 阶段三：固定算法与应用编排

变更：

- 实现资料分类、候选提取、程序校验、灵魂综合和评测；
- 固定模型、参数、提示词、提供器和输入快照；
- 完成确认时复用现有内容领域规则，并通过蒸馏仓储接缝的跨聚合事务原子创建人物、初始当前灵魂版本及资料关系。

验证：

- 每个模型步骤最多两次尝试；
- 长网络调用期间不持有 SQLite 事务；
- OpenViking 与 FTS5 返回相同的允许集合语义；
- 候选编辑会使旧评测失效，候选确认时资料或状态变化不会重复创建人物。

### 阶段四：后台工作区

变更：

- 人物创建改为异步工作区；
- 增加覆盖摘要、证据检查、候选编辑和评测展示；
- 保持人物创建后的灵魂草稿发布入口不变。

验证：

- 组件测试覆盖两个检查点、失败、取消、恢复和重复点击；
- `pnpm typecheck`；
- 核心浏览器闭环从人物创建进入灵魂发布和一次图文生成。

### 阶段五：外部采集协作

扩展现有资料创建契约，使外部 Agent 可以随文本提交可选来源地址、作者、时间和原始来源键，并更新人样 Skill 文档。该阶段仍不允许公共接口触发蒸馏；只有在产品范围明确允许后，才增加网页、PDF、视频转写或公共蒸馏运行能力。

## 19. 测试矩阵

| 层级 | 必测内容 |
|---|---|
| 领域单元测试 | 状态机、来源去重、引用定位、候选降级、冲突保留、硬软门禁 |
| 应用单元测试 | 固定步骤顺序、快照、失败归一化、取消安全点、确认幂等 |
| SQLite 集成测试 | 迁移、事务、并发确认、重启恢复、资料删除后的历史清除 |
| 模型契约测试 | 四步输出 Schema、非法引用重试、无有效候选、未知边界失败 |
| 上下文契约测试 | OpenViking 与 FTS5 的允许集合、排序后复验、禁止未知 URI |
| 组件测试 | 创建输入、覆盖确认、候选校准、编辑后评测失效、评测失败、恢复页面 |
| 端到端测试 | 无资料创建、有资料蒸馏、冲突资料、OpenViking 故障降级、最终发布与生成 |
| 备份恢复测试 | 运行、输入、候选、证据、评测和人物关联完整恢复 |

自动化模型替身至少提供以下夹具：

1. 正常多来源人物；
2. 无资料人物；
3. 相同采访多次转载；
4. 早期与近期观点冲突；
5. 模型引用不存在资料；
6. 引用文本无法定位；
7. 候选只包含通用 AI 话术；
8. 未知问题被确定性补全；
9. 评测步骤超时；
10. 用户确认时运行已经被其他请求确认。

## 20. 完成标准

人物蒸馏只有同时满足以下条件才算完成：

1. 用户可以用自然语言和可选资料启动人物创建，不需要选择来源模式。
2. 覆盖检查能够区分资料角色、来源关系、覆盖维度和独立来源。
3. 所有确定性候选都能定位到本次 SQLite 输入快照。
4. 重复来源不会虚增证据，冲突不会被静默消除。
5. 候选灵魂保持单文本契约，不携带来源目录、工具指令或流程元话术。
6. 已知事实、未知边界、表达方式、反事实和冲突评测均保存可审计结果，并与候选正文哈希绑定。
7. 未经最终人工确认不会创建人物；确认后创建的初始当前灵魂版本才会影响新任务。
8. 进程重启、模型失败和 OpenViking 故障都有稳定状态与恢复路径。
9. SQLite 仍是唯一业务事实源，备份恢复不依赖 OpenViking。
10. `pnpm check`、相关集成测试和核心 `pnpm test:e2e` 全部通过。

## 21. 实施前默认决策

如果没有新的产品决策，实施按以下默认值推进：

1. 所有人物创建统一进入蒸馏流程，资料可选，不增加人物来源模式。
2. 首期仅支持已导入文本资料，不内建联网采集。
3. 资料覆盖确认和最终候选确认是两个强制检查点。
4. 未知边界、证据引用和 Token 预算属于硬门禁；资料覆盖率和风格评分属于软门禁。
5. 评测失败不能默认确认；用户必须修改并重新评测，不提供无理由绕过。
6. 蒸馏完成原子创建人物与初始当前灵魂版本；后续修改不绕过灵魂草稿发布流程。
7. 首期不开放公共蒸馏接口。
