## 完成度审计修复一：自然语言人物草稿

对照产品范围唯一事实源后确认，原实现只能手工提交完整结构化人物快照，没有实现“从自然语言创建结构化人物候选档案”。本次补齐独立编辑闭环：

1. 新增 `POST /api/v1/personas/draft`，控制器只解析共享 Schema 并调用生成应用服务。
2. 应用服务读取可选已发布世界与最多 8 项选定资料，通过文本模型生成 `name` 和完整人物快照。
3. 用户明确人设高于参考资料；只有 `canon_fact` 可作为原著事实，证据不足字段保持未知。
4. 草稿不写数据库、不创建版本、不自动发布；页面只把结果填入结构化表单，必须由用户检查并保存。
5. 单项资料和世界正文分别限制为前 5000 字和前 10000 字，发生截断时返回并展示明确提示。
6. 文本模型未配置时 AI 按钮禁用，原手工创建路径保持完整。

组件按职责拆分：创建页只编排请求，`PersonaDraftAssistant` 采集自然语言与参考上下文，`PersonaForm` 只编辑和校验结构化候选。分层测试继续保证控制器不访问模型实现，应用服务只依赖端口。

验证结果：

- 类型检查通过。
- 23 个测试文件、113 项测试全部通过。
- 新测试覆盖资料去重、事实角色提示、生成不落库、模型关闭、草稿助手事件和人工提交门禁。
- Nuxt/Nitro 生产构建通过，并生成静态优先的 `personas/draft.post` 服务端路由。

本项只证明软件契约；自然语言草稿的实际内容质量仍纳入真实文本模型手工验收。

## 完成度审计修复二：运行限制与供应商用量

原实现只有最大输出 Token、最大证据块和最大文字块三项相关参数，且每个块固定执行最多两次，无法完整执行文档规定的运行级硬限制。本次补齐：

1. 参数快照新增最大图片块、单次提示最大字符、运行最大已报告 Token 和单块累计尝试四项限制。
2. 文字块与图片块分别计数；格式模板的块总数同时受模板与运行快照约束。
3. 调用前按系统提示与用户提示的准确字符总数校验，不使用与供应商分词器不一致的本地 Token 估算。
4. 兴趣、规划和文字块调用累计供应商实际报告的用量；结构修复失败、自动任务重试和手工重试均保留既有用量。
5. 运行达到已报告 Token 上限后不再创建调用；收到导致超限的响应时先保存其用量，再以 `TASK_LIMIT_EXCEEDED` 结束。
6. 单块尝试上限覆盖首次执行、依赖失败、整文重试和单块重试；锁定状态优先返回 `BLOCK_LOCKED`。
7. 参数管理页可编辑和查看全部限制；运行页显示聚合用量，块卡片显示单次用量与尝试耗尽原因。
8. 新字段使用共享 Schema 默认值兼容旧参数 JSON，真实旧数据库通过仓储读取测试，无需新增迁移。

验证覆盖提示字符超限不调用模型、结构修复用量合计、失败响应用量跨任务累计、供应商响应后取消仍保存用量、运行 Token 超限停止、图文块独立限额、单块尝试耗尽、运行聚合展示及旧快照兼容。验证结果：

- 类型检查通过。
- 23 个测试文件、118 项测试全部通过。
- Drizzle 迁移快照一致性检查通过；本改动使用 JSON 默认值兼容旧数据，没有新增数据库迁移。
- Nuxt/Nitro 生产构建通过。

## 完成度审计修复三：可复现 Playwright 核心闭环

原测试方案声明使用 Playwright，但仓库没有依赖、配置或可重复执行的浏览器测试。本次建立最小高价值闭环：

1. 新增 `pnpm test:e2e`，每次删除测试独占的 `.playwright-data`，从空 SQLite 和首次设置状态开始。
2. Playwright 自动执行生产构建并启动真实 Nitro Node Server，不使用会改变回环来源语义的开发代理。
3. 会话密钥每次随机生成；文本模型使用独立本地 OpenAI-compatible 协议替身，不连接真实收费服务，也不保存真实密钥。
4. Chromium 完成首次设置、退出、重新登录、原创人物创建、候选发布、文档规划、人工确认、Worker 执行、安全预览以及 HTML、Markdown、Txt 三次真实下载。
5. 测试通过角色、标签和可见名称定位，不依赖样式类或内部 DOM 快照；失败时保留截图和 trace，成功不保留运行数据到 Git。

浏览器闭环实际发现并修复三项此前组件测试未暴露的问题：全局认证中间件在异步请求后调用 `navigateTo` 导致 SSR 上下文丢失；根组件没有挂载 `NuxtLayout`；工作台原生下拉框缺少可访问名称。三项均按页面真实语义修复，没有绕过首次设置的严格回环门禁。

验证结果：

- Playwright Chromium 核心流程 1 项通过；加入管理状态断言后，浏览器步骤约 6.9 秒。
- E2E 内部生产构建、Nitro 启动、本地协议替身和三格式下载全部通过，总耗时约 23.0 秒。

## 完成度审计修复四：管理状态、运行限制与证据标识

原仪表盘只展示人物、世界、资料和 SQLite/Worker 状态，没有实现设计文档要求的最近人物、活动运行、待处理反馈和外部能力；全局导航也没有账户、后台任务数和能力影响。系统设置虽然支持 OpenViking、备份和审计，但缺少账户与默认运行限制。运行证据只有角色和哈希，兴趣判断的模型推断与支持、反对证据关系不够明确。

本次按当前真实用途完成以下最小闭环：

1. 任务数据端口新增只读队列摘要，SQLite 精确统计 `queued`、`running` 和 `cancel_requested`，终止任务不计入后台任务数；系统健康接口返回该摘要。
2. 全局布局每五秒刷新系统健康状态，显示当前管理员、后台任务总数、文本/图片能力和本地或语义检索状态；状态文字明确，不只依赖颜色。
3. 仪表盘复用现有人物、运行、反馈、修订提案和能力接口，展示最近人物、活动运行、待处理反馈、后台任务与外部能力；任一摘要请求失败时提供统一重试入口。
4. 系统能力接口返回未选择参数方案时实际使用的默认运行参数；设置页显示文本、图片、OpenViking 的能力影响、默认块数、尝试数、提示字符和 Token 限制，以及当前唯一管理员和本机密码重置边界。
5. 兴趣判断明确标记为“AI 模拟推断，不是人物事实”；证据快照标识支持或反对关系，并显示可追踪资料链接或“人物版本内设定”。
6. 资料详情首次加载失败后，重试成功会安全初始化编辑表单；后续关联刷新不会覆盖尚未提交的正文编辑。

页面仍只使用 `useFetch` 和 HTTP 接口编排数据。任务统计由 `SystemApplicationService` 通过 `TaskQueueStatusReader` 获取；SQLite 查询只存在于基础设施适配器。默认布局只负责取数和轮询，`NavigationStatus`、`DashboardWorkPanel`、`CapabilityStatusPanel` 均使用类型化 Props，不自行访问服务端。

## 异常退出与任务恢复

1. 让兴趣任务进入 `running`，并保持文本供应商请求未完成。
2. 对生产进程发送 `SIGKILL`，不执行正常关闭钩子。
3. 把测试任务租约调整为已过期，模拟真实等待超过租约时间。
4. 保持同一数据目录重启生产服务。
5. 单实例锁识别原 PID 已退出并清理失效锁。
6. Worker 恢复过期任务，以第二次尝试完成原任务。

结果：通过；运行最终 `succeeded`，原任务 `attemptCount=2`，没有创建重复业务运行。
