## 完成度审计修复一：自然语言人物草稿

对照产品范围唯一事实源后确认，原实现只能手工提交完整结构化人物快照，没有实现“从自然语言创建结构化人物候选档案”。本次补齐独立编辑闭环：

1. 新增 `POST /api/v1/personas/draft`，控制器只解析共享 Schema 并调用生成应用服务。
2. 应用服务读取可选已发布世界与最多 8 项选定资料，通过文本模型生成 `name` 和完整人物快照。
3. 用户明确人设高于参考资料；只有 `canon_fact` 可作为原著事实，证据不足字段保持未知。
4. 草稿不写数据库、不创建版本、不自动发布；页面只把结果填入结构化表单，必须由用户检查并保存。
5. 单项资料和世界正文分别限制为前 5000 字和前 10000 字，发生截断时返回并展示明确提示。
6. 文本模型未配置时 AI 按钮禁用，原手工创建路径保持完整。

组件按职责拆分：创建页只编排请求，`PersonaDraftAssistant` 采集自然语言与参考上下文，`PersonaForm` 只编辑和校验结构化候选。分层测试继续保证控制器不访问模型实现，应用服务只依赖端口。

验证结果：

- 类型检查通过。
- 23 个测试文件、113 项测试全部通过。
- 新测试覆盖资料去重、事实角色提示、生成不落库、模型关闭、草稿助手事件和人工提交门禁。
- Nuxt/Nitro 生产构建通过，并生成静态优先的 `personas/draft.post` 服务端路由。

本项只证明软件契约；自然语言草稿的实际内容质量仍纳入真实文本模型手工验收。

## 完成度审计修复二：运行限制与供应商用量

原实现只有最大输出 Token、最大证据块和最大文字块三项相关参数，且每个块固定执行最多两次，无法完整执行文档规定的运行级硬限制。本次补齐：

1. 参数快照新增最大图片块、单次提示最大字符、运行最大已报告 Token 和单块累计尝试四项限制。
2. 文字块与图片块分别计数；格式模板的块总数同时受模板与运行快照约束。
3. 调用前按系统提示与用户提示的准确字符总数校验，不使用与供应商分词器不一致的本地 Token 估算。
4. 兴趣、规划和文字块调用累计供应商实际报告的用量；结构修复失败、自动任务重试和手工重试均保留既有用量。
5. 运行达到已报告 Token 上限后不再创建调用；收到导致超限的响应时先保存其用量，再以 `TASK_LIMIT_EXCEEDED` 结束。
6. 单块尝试上限覆盖首次执行、依赖失败、整文重试和单块重试；锁定状态优先返回 `BLOCK_LOCKED`。
7. 参数管理页可编辑和查看全部限制；运行页显示聚合用量，块卡片显示单次用量与尝试耗尽原因。
8. 新字段使用共享 Schema 默认值兼容旧参数 JSON，真实旧数据库通过仓储读取测试，无需新增迁移。

验证覆盖提示字符超限不调用模型、结构修复用量合计、失败响应用量跨任务累计、供应商响应后取消仍保存用量、运行 Token 超限停止、图文块独立限额、单块尝试耗尽、运行聚合展示及旧快照兼容。验证结果：

- 类型检查通过。
- 23 个测试文件、118 项测试全部通过。
- Drizzle 迁移快照一致性检查通过；本改动使用 JSON 默认值兼容旧数据，没有新增数据库迁移。
- Nuxt/Nitro 生产构建通过。

## 完成度审计修复三：可复现 Playwright 核心闭环

原测试方案声明使用 Playwright，但仓库没有依赖、配置或可重复执行的浏览器测试。本次建立最小高价值闭环：

1. 新增 `pnpm test:e2e`，每次删除测试独占的 `.playwright-data`，从空 SQLite 和首次设置状态开始。
2. Playwright 自动执行生产构建并启动真实 Nitro Node Server，不使用会改变回环来源语义的开发代理。
3. 会话密钥每次随机生成；文本模型使用独立本地 OpenAI-compatible 协议替身，不连接真实收费服务，也不保存真实密钥。
4. Chromium 完成首次设置、退出、重新登录、原创人物创建、候选发布、文档规划、人工确认、Worker 执行、安全预览以及 HTML、Markdown、Txt 三次真实下载。
5. 测试通过角色、标签和可见名称定位，不依赖样式类或内部 DOM 快照；失败时保留截图和 trace，成功不保留运行数据到 Git。

浏览器闭环实际发现并修复三项此前组件测试未暴露的问题：全局认证中间件在异步请求后调用 `navigateTo` 导致 SSR 上下文丢失；根组件没有挂载 `NuxtLayout`；工作台原生下拉框缺少可访问名称。三项均按页面真实语义修复，没有绕过首次设置的严格回环门禁。

验证结果：

- E2E 内部生产构建、Nitro 启动、本地协议替身和三格式下载全部通过，总耗时约 23.0 秒。

## 完成度审计修复四：管理状态、运行限制与证据标识

原仪表盘只展示人物、世界、资料和 SQLite/Worker 状态，没有实现设计文档要求的最近人物、活动运行、待处理反馈和外部能力；全局导航也没有账户、后台任务数和能力影响。系统设置虽然支持 OpenViking、备份和审计，但缺少账户与默认运行限制。运行证据只有角色和哈希，兴趣判断的模型推断与支持、反对证据关系不够明确。

本次按当前真实用途完成以下最小闭环：

1. 任务数据端口新增只读队列摘要，SQLite 精确统计 `queued`、`running` 和 `cancel_requested`，终止任务不计入后台任务数；系统健康接口返回该摘要。
2. 全局布局每五秒刷新系统健康状态，显示当前管理员、后台任务总数、文本/图片能力和本地或语义检索状态；状态文字明确，不只依赖颜色。
3. 仪表盘复用现有人物、运行、反馈、修订提案和能力接口，展示最近人物、活动运行、待处理反馈、后台任务与外部能力；任一摘要请求失败时提供统一重试入口。
4. 系统能力接口返回未选择参数方案时实际使用的默认运行参数；设置页显示文本、图片、OpenViking 的能力影响、默认块数、尝试数、提示字符和 Token 限制，以及当前唯一管理员和本机密码重置边界。
5. 兴趣判断明确标记为“AI 模拟推断，不是人物事实”；证据快照标识支持或反对关系，并显示可追踪资料链接或“人物版本内设定”。
6. 资料详情首次加载失败后，重试成功会安全初始化编辑表单；后续关联刷新不会覆盖尚未提交的正文编辑。

## 完成度审计修复五：文档、接口与 OpenViking 边界

对 README、产品、领域、架构、数据、接口、反馈、导出、管理、测试、部署和阶段文档逐项对照真实端点、Drizzle Schema、应用服务与基础设施实现，删除了仍被写成当前能力的旧设计草案：

1. OpenViking 只同步资料正文，运行检索只允许使用当前人物或世界已关联的资料；人物版本、反馈、候选记忆和运行历史始终保存在 SQLite，不提供反馈语义召回。
2. 资料角色统一为 `canon_fact`、`reference`、`style_sample`；世界由独立世界对象承载。
3. 候选记忆只由用户明确确认的长期人物反馈产生；场景、重复行为和重复反馈尚不自动聚合。一项反馈最多创建一个候选记忆和一个修订提案。
4. 参数解析统一为系统默认参数或用户选择的完整不可变方案；格式模板仅提供结构指导和块数范围。
5. 接口清单删除未实现的详情、参数解析、备份查询和在线恢复接口，补入实际存在的版本比较、资料检索、资产、健康与审计接口；成功响应统一为 `{ data }`。
6. 数据文档移除两项不存在的旧草案表，补齐审计、图片资产、反馈建议/确认、候选记忆和上下文同步等实际表。
7. 单格式导出按请求即时生成：无图片时返回单文件，有图片时 ZIP 只包含一个目标文档、`manifest.json` 和被引用资源，不保存导出历史。
8. 在线备份使用 SQLite 一致性副本及副本中的文件引用白名单，不暂停所有写入；密码重置、备份验证和恢复只通过本机 CLI 执行。

本次只修正文档，没有修改运行代码、Schema 或迁移。验证以真实端点枚举、Schema 表名枚举、关键冲突词扫描和 `git diff --check` 为准，不重复执行已在前一闭环通过的全量测试与生产构建。

## 真实模型生产验收

验收使用 Git 忽略的仓库外配置、独立临时 SQLite 和真实 `.output/server/index.mjs`。前置检查只输出以下非敏感信息：

- 文本模型：`gpt-5.6-luna`，接口来源 `http://10.10.10.1:20003`。
- 图片模型：`gpt-image-2`，接口来源 `http://10.10.10.1:20003`。
- OpenViking 当前关闭，运行固定使用 `contextProvider=sqlite_fts5`；这符合其可选能力决策。

### 构建密钥隔离

首次按真实配置构建时发现 Nuxt 会自动读取根目录 `.env`，且 `nuxt.config.ts` 直接读取会话密钥，存在把运行密钥写入生产产物的风险。修复如下：

1. `pnpm build` 显式使用只含说明且无任何赋值的 `.env.build`，不再读取本地 `.env`。
2. 会话配置默认值固定为空，只允许启动进程通过 `NUXT_SESSION_PASSWORD` 覆盖。
3. 单元测试同时约束构建命令、空构建环境和禁止构建期直接读取会话密钥。
4. 使用三个唯一长哨兵分别模拟会话、文本和图片密钥，在环境变量已存在的情况下重新构建；三个哨兵进入 `.output` 的文件数均为 0。
5. 真实运行配置只在 `node --env-file=.env .output/server/index.mjs` 启动时注入，构建产物可以与运行密钥分离。

### 真实模型发现与修复

首轮兴趣判断返回完整顶层字段，但模型把 `factors` 生成为字符串数组；首轮文档规划把 `requestedFormats` 生成为带说明的对象数组。TypeScript Schema 不会自动传给模型，原提示仅列字段名，约束不足。

通过只记录字段名、类型和 Zod 错误路径的脱敏诊断确认根因，没有输出模型原文、请求密钥或供应商私有响应。随后把提示版本提升到 `artifact-v4`：

- 兴趣提示明确 factors 每项的 `dimension`、`score`、`explanation`，枚举和数值范围。
- 规划提示明确标量、字符串数组、块对象、依赖 key、图片视觉简报与宽高比枚举。
- `requestedFormats` 明确限定为 `html`、`markdown`、`txt` 字符串数组，禁止格式说明对象。
- 单元测试固定两项真实模型曾误解的嵌套契约。

修复后真实模型结果：

1. 原创人物“顾岚”无外部资料时完成兴趣判断，明确列出人物经历、具体日期和物件背景均未知，没有虚构原著事实。
2. 资料型人物“沈砚”引用唯一 `canon_fact` 证据，正确指出霜月十三日首次看见且拒绝触碰；没有把霜月十二日操作和收藏的断言称为原著事实。
3. 混合人物“闻秋”同时命中人物设定、`canon_fact` 和冲突 `reference`，按“设定—原文—推断”分层回答，并拒绝把二次推测升级为事实。
4. 同一原创人物先完成兴趣判断，再完成图文创作；模型初始规划包含 5 个图文块并进入 `awaiting_confirmation`。
5. 用户把规格修订为固定标题、正文和插图三块，限定三种格式、正文上限、事实边界及视觉简报；最终确认规格与输入逐字段一致。
6. 两个文本块分别生成“旧物传闻三步核验”和 500 字以内正文；正文按记录出处、交叉核对、明确未知组织，且没有虚构人物经历。
7. 图片模型生成 2566878 字节 PNG，本地魔数、媒体类型、大小和 SHA-256 均保存；人工目视确认是低饱和蓝灰档案桌面，含旧信件、索引卡、手套和铅笔，无可见文字、水印或人物正脸。
8. HTML、Markdown、Txt 同时渲染成功；HTML 和 Markdown 引用同一本地图片，Txt 保留标题与可读文本。图片失败和部分成功路径继续由确定性协议黑盒覆盖。
9. 长期负面反馈被真实模型以 0.99 置信度归为人物变化。用户确认修改 `constraints` 后，硬规则判为 `critical` 且存在证据冲突。
10. 固定安全用例评测正常执行：基础版 1.0，候选版 0.2；候选缺少“资料不足”、低于最低分且退化超限，提案进入 `evaluation_failed`。活动人物版本未变化，候选版本未发布。
