# 统一心智模型需求与实施设计记录

## 本阶段目标

在修改业务代码前，统一世界、人物、灵魂、成长和记忆的领域边界，明确原始数据、迭代审核、OpenViking 和提示词 Token 预算，并形成可按阶段实施的开发设计。

本阶段只修改文档，不执行数据库迁移或业务代码改造。

## 已确认决策

1. 世界是一种特殊模拟对象，拥有灵魂和成长，不拥有记忆。
2. 人物拥有灵魂、成长和记忆；一个世界包含多个人物，一个具体人物只属于一个世界。
3. 世界和人物灵魂均使用有序自由章节，不再使用固定八字段或世界单正文。
4. 当前已发布灵魂只读；修改创建草稿，发布后形成不可变版本；回滚基于历史创建新草稿。
5. 世界成长来自已启用世界资料；人物成长来自已启用人物反馈资料。
6. 人物记忆来自人物写作、兴趣判断和分析等任务形成的有效处理记录。
7. 成长原始资料和处理记录按条展示，支持批量启用、禁用和分析；人物反馈资料支持删除。
8. 删除或禁用原始数据不直接改变已确认成长或记忆，只更新来源可用状态并提示重新分析；删除人物反馈资料会同步清除分析输入中的对应正文，不能从历史恢复原文。
9. 分析结果支持新增、修订、合并、取代、停用和保持不变，必须经过人工审核。
10. 记忆转成长必须先转为人物反馈资料；成长进入灵魂必须经过“吸收到灵魂”和发布流程。
11. SQLite 始终是唯一业务事实源；OpenViking 负责隔离 Resource、Peer Session、派生素材和相关性排序。
12. OpenViking 使用 Account=租户、User=世界、Peer=人物；世界资料进入 User Resource，人物资料和反馈资料进入 Peer Resource，人物处理过程进入 Peer Session。
13. 运行前执行总输入、世界、人物、灵魂、成长、记忆和资料 Token 预算；灵魂不允许运行时随机截断。
14. 控制器和 Worker 只调用应用服务，应用服务通过端口访问数据层和外部能力。

## 当前代码差距

文档确认后，现有实现仍存在以下差距，不能视为功能完成：

- `PersonaSnapshot` 及其 Zod Schema 仍固定八字段。
- `WorldSnapshot` 仍只有单一 `content`。
- `PromptBuilder` 仍直接序列化旧人物和世界快照，没有心智分类和 Token 预算。
- 现有成长只有简单记录和 FTS5 检索，没有原始反馈资料、修订、分析批次和审核服务。
- 现有记忆只有简单候选状态，没有处理记录、累计分析、独立证据和修订。
- OpenViking Session 与派生门禁仍按旧反馈模型实现。
- 人物和世界页面尚未实现目标工作区。

## 实施顺序

1. 共享契约与数据迁移。
2. 世界与人物灵魂闭环。
3. 世界与人物成长闭环。
4. 人物处理记录与记忆闭环。
5. 提示词预算与运行快照。
6. 工作区重构和总验收。

每个阶段完成后分别执行范围匹配的测试、构建、开发记录、Git 提交和推送。
